## What broke — two distinct hardware-side problems

### 1. Native USB Serial/JTAG won't enumerate on this board

The current `sdkconfig.defaults` sets `CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y` (commit `00facad`, 2026-04-27). That routes the IDF console to the ESP32-S3's native USB peripheral on GPIO 19/20, which most dev boards expose on a separate "USB" USB-C connector (vs. the "UART" port that goes through CH340K).

On this board's "USB" port:

- Windows enumerates the device but reports `Unknown USB Device (Device Descriptor Request Failed)` with VID/PID `0000/0002` in Error state.
- User-facing balloon: "device not recognized."
- Tried multiple cable swaps and orientations.

So no console output reaches the laptop via the native USB path — `idf.py monitor` over the chip's native USB gets nothing.

### 2. Console workaround (rerouting to UART0) succeeded but chip stays in DOWNLOAD mode after flash

Patched `firmware/sdkconfig` (gitignored — laptop-local only):

```
# CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG is not set
CONFIG_ESP_CONSOLE_UART_DEFAULT=y
CONFIG_ESP_CONSOLE_UART_NUM=0
# CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG_ENABLED is not set
```

Rebuilt + reflashed cleanly. But every reboot of the chip lands in:

```
ESP-ROM:esp32s3-20210327
rst:0x1 (POWERON), boot:0x0 (DOWNLOAD(USB/UART0))
waiting for download
```

`boot:0x0` means GPIO0 + GPIO46 strap pins were both low at reset → ROM download mode, not the flashed firmware. That's why no console output ever appears: the firmware never runs.

**Tried, didn't work:**
- `idf.py flash` with default `--after hard_reset` (the standard polarity esptool uses)
- `python -m esptool ... --before default_reset --after hard_reset run` (explicit run command, same polarity)
- pyserial RTS pulse with `dtr=False` to keep BOOT (GPIO0) high during reset
- pyserial RTS pulse with `dtr=True` (inverted polarity) — chip didn't even reset
- Opened the port with `serial_for_url(do_not_open=True)`, set DTR/RTS before opening, opened — same result

The CH340K's auto-reset transistor circuit on this specific board appears to have a polarity / wiring different from what esptool's reset sequences expect. Repeatable across all attempts.

**Untested next step (paused before trying):** physically press the dev board's **EN/RST button** after the flash command finishes. Bypasses the auto-reset circuit entirely. User stepped away before we could confirm.

## Notes on the working environment

- **`[System.IO.Ports.SerialPort]::GetPortNames()` is not reliable on this laptop's Windows install** — saw a "phantom COM5" persist even after the device was unplugged and after the actual device showed up on a different number. Use `Get-PnpDevice -Class Ports -PresentOnly` for authoritative state.
- COM port numbers reassigned freely between unplug/replug cycles (COM5 → COM9 → COM10 in this session). Always re-query before invoking esptool.
