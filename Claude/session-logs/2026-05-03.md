## 1. Camera — CAM1 IMX219 not responding

User reported the camera was working then randomly stopped. Probed the
Jetson over Tailscale (`ssh jetson`):

- `/dev/video*` does not exist.
- `i2cdetect -y -r 9` (CAM1, port C, the one with the working clamp) shows
  the bus empty — nothing acks at 0x10.
- `dmesg` shows the same `imx219 9-0010: imx219_board_setup: error during
  i2c read probe (-121)` from prior incidents (see
  `memory/hardware_camera_clamp.md`).
- Bus 10 (CAM0, broken-clamp port) also `-121`, as always.

User cycled power 50+ times, reseating the ribbon between each cycle. None
of the 79 probe attempts during a 10-minute polling loop saw the chip come
up. This is past "finicky seating." Almost certainly:

- damaged ribbon cable (boat vibration), or
- the IMX219 module itself is dead.

**Action items for next session:**
- Swap to a known-good 22-pin Jetson CSI ribbon and try again.
- If still `-121`, swap the IMX219 module.
- If still `-121` with both swapped, the carrier connector is the next
  suspect.
- Software is not the issue; do not waste cycles on driver/JetPack work.

## 2. Follower drone firmware integration

Pivoted after camera was declared a hardware problem. User asked to fold
`Claude/project-docs/FollowerDroneCode.txt` (Jamie's standalone Arduino
sketch for a baby drone) into the existing ESP-IDF firmware so a single
binary can be flashed to every ESP32 in the swarm, with role decided at
provisioning time (NVS flag) instead of build time.

User's deployment intent — keep this in mind:

> Production: every hull has Jetson + Pixhawk + ESP32. Sensors vary per
> hull as needed. ESP32 only does swarm coordination; Jetson drives the
> Pixhawk.
>
> Demo: leader hull is full stack. Follower hulls are stripped down
> (ESP32 + Pixhawk, no Jetson) for cost. ESP32 drives the Pixhawk
> directly via the new `pixhawk_link` path.

So `pixhawk_link` is **demo-only**, gated by an NVS-backed `has_jetson`
flag. Flag default is `true` (production). Demo followers run
`set_jetson 0` at provisioning to enable `pixhawk_link`.

### What landed

New files in `firmware/main/`:

- **`pixhawk_link.{c,h}`** — UART2 (TX=GPIO38, RX=GPIO39, 57600 baud,
  MAVLink v2). RX task parses inbound HEARTBEAT to track Pixhawk arm +
  flight mode. TX task sends 1 Hz heartbeat + non-blocking
  GUIDED → ARM → SET_POSITION_TARGET ladder, retry-gated, rate-limited
  to 0.5 s between targets. Anchor stale > 5 s → Pixhawk to HOLD.
  Subscribes to `MSG_TYPE_GPS_ANCHOR` directly via the existing
  multi-callback fan-out in `swarm_transport`. Console: `px_status`,
  `px_stop`. Emergency stop wired to inbound `CMD_STOP` from leader.

- **`mav_min.{c,h}`** — minimal MAVLink v2 wire encoder for HEARTBEAT,
  SET_MODE, COMMAND_LONG (arm), SET_POSITION_TARGET_GLOBAL_INT, plus
  inbound HEARTBEAT parser. CRC_EXTRA values from official
  `common.xml`. Hand-rolled — pulling in the full MAVLink C library
  is hundreds of files for four messages.

- **`latlon_offset.h`** — header-only port of
  `jetson/swarm_coordinator.py:offset_to_latlon`. Combines anchor +
  formation offset → target lat/lon. Same flat-earth math as the
  Jetson side so leader (Jetson) and followers (`pixhawk_link`) agree
  on geometry.

Modified:

- **`node_config.{c,h}`** — added persistent `has_jetson` flag (NVS
  key `has_jetson`, default `true`). Console command `set_jetson <0|1>`.
  Surfaced in existing `info` output.

- **`main.c`** — gated `pixhawk_link_init`, `pixhawk_link_start`, and
  console-command registration on `!node_config_has_jetson()`. Wired
  `on_position_assigned → pixhawk_link_set_offset` and
  `on_command_received(CMD_STOP) → pixhawk_link_emergency_stop`.

- **`sensor_bridge.c`** — added active EZO pH polling (`R\r` per
  cycle, mirrors Jamie's `Sensor_DataLog.py`). On Jetsonless hulls,
  also emits Jamie's CSV format alongside the existing TEMP:/SAL:/PH:
  line:

      SLOG,<ms_since_boot>,<ph>,<tds_ppm>,<temp_c>

  Capture via any external serial logger. **Did not** add SPIFFS-
  backed local file logging — that would require a partition table
  change which can wipe NVS-stored `node_id` on existing chips.

- **`swarm_bridge.c`** — pre-existing bug: called
  `membership_get_count()` without including `membership.h`. Older
  IDF versions tolerated the implicit declaration; v5.5.2 toolchain
  rejects it. Added the missing include.

- **`CMakeLists.txt`** — registered `pixhawk_link.c`, `mav_min.c`.

### Architecture note — Sensor_DataLog.py

`Sensor_DataLog.py` at the repo root is Jamie's MicroPython logger.
**Cannot** be flashed alongside ESP-IDF firmware (different runtimes).
Its useful behaviors (active polling + CSV column order) are now in
`sensor_bridge.c`. The .py file is left in place as Jamie's reference.

### Per-hull provisioning

```
set_node_id <N>       # unique 1..254
set_jetson 0          # demo follower hulls only; production stays default 1
<press reset>
```

### Demo follower wiring

```
ESP32 GPIO 38 (TX) -> Pixhawk TELEM1 RX
ESP32 GPIO 39 (RX) -> Pixhawk TELEM1 TX
GND                -> GND
```

Pixhawk TELEM1 (SERIAL2) defaults: 57600 baud, MAVLink2 protocol — no
Pixhawk-side reconfiguration needed.

### Demo flow

1. Leader (Jetson hull): GUI → "Start Swarm Mode" → leader's
   `swarm_bridge` broadcasts `MSG_TYPE_GPS_ANCHOR` over ESP-NOW.
2. Followers (Jetsonless hulls): receive anchor + their formation
   offset → `pixhawk_link` computes target → SET_MODE GUIDED → ARM →
   SET_POSITION_TARGET_GLOBAL_INT to local Pixhawk.
3. Leader sends `CMD_STOP` → followers HOLD + disarm immediately.

### Pre-existing protocol issue (documented, not fixed today)

`gps_anchor_payload_t.heading_cdeg` is `int16_t`, which overflows for
heading values 327.68°..359.99°. `pixhawk_link.c::recover_heading_deg`
does an opportunistic recovery (treat negative cdeg as the uint16_t
equivalent). Real fix: change struct to `uint16_t` — minor protocol
change, both ends.
