## 1. Scope, and how the work was phased

Four phases, each ending at a state the mock could exercise:

- **Phase A — Observability.** Expanded the Pixhawk-side telemetry dict with servo PWM, battery, GPS quality, EKF health, and per-link freshness ages. Added a dedicated Telemetry tab and a rolling black-box JSONL log. Built `ws_peek.py` for pure-SSH verification of the stream without a browser.
- **Phase B — Safety core.** GCS-heartbeat watchdog that fires a configurable failsafe (HOLD / RTL / DISARM) on link loss. Always-visible E-Stop in the header. Pre-arm checklist on the Dashboard that disables START MISSION until every required row is green. Admin auth (opaque in-memory session tokens hashed from an env-var password) that unlocks the bypass. Web Audio alerts for failsafe / low battery / link loss / E-Stop. Failsafe banner across the top when tripped.
- **Phase C — Control & recording.** Admin-gated Manual tab with virtual sliders, USB Gamepad API support, and ARM/DISARM/set-mode buttons; sends RC_CHANNELS_OVERRIDE at 20 Hz while engaged; auto-releases on tab change or navigation away. Dual-save video: when the user clicks Start Recording, the browser also starts a `MediaRecorder` on the WebRTC stream so the footage writes to the GCS disk as a `.webm` alongside the Jetson's own recording. Save-confirm toasts with filenames for CSV / video / stop-recording.
- **Phase D — Mission authoring.** Draw-fence polygon flow that uploads to the Pixhawk via the legacy FENCE_POINT protocol, sets `FENCE_ENABLE` / `FENCE_ACTION` / `FENCE_TYPE` appropriately, and does client-side breach checking as a belt-and-suspenders. Survey/lawnmower generator: draw a polygon, specify line spacing in meters, generates boustrophedon-ordered waypoints that sweep the whole area via horizontal-line polygon-edge intersections. Mission templates that save/load/delete named waypoint sets in `localStorage`.

## 3. Admin auth model

- Password read from `AQUABOT_ADMIN_PW` env var at service startup. If unset, admin features stay disabled — Manual tab stays locked, pre-arm bypass checkbox hidden.
- Plaintext password is hashed with SHA-256 at load. Never touches disk.
- Login action returns an opaque 24-byte token (`secrets.token_urlsafe`). Kept in an in-memory set on the server; stored in `sessionStorage` on the client.
- Admin-gated actions require the token in the WebSocket JSON payload: `set_mode`, `manual_rc`, `manual_release`. Server uses `hmac.compare_digest` for the constant-time check.
- Client tab visibility only — the Manual tab simply reveals its controls when `aquaAdminActive()` returns true; nothing security-sensitive lives in the client. Real gate is on the server.

Set the password at service startup, e.g. in the systemd unit:
```
Environment=AQUABOT_ADMIN_PW=pickone
```

## 4. Mock server

Runs anywhere with Python + `flask` + `websockets`:
```
pip install flask websockets
python3 jetson/tools/mock_server.py
# -> http://localhost:5000
# admin pw: demo
```

Serves the real templates and static directories from the repo so anything you edit there shows up on refresh. `TEMPLATES_AUTO_RELOAD = True` is set so Jinja picks up template edits without a server restart — this was needed after a gotcha where the initial mock kept serving a cached compiled template across several rounds of edits.

What the sim does:
- Battery decays (faster while armed).
- Vehicle drives a 10 m circle when armed in AUTO; head toward home in RTL; zero speed in HOLD; light drift in MANUAL.
- Sensor values oscillate with small noise.
- All link-age counters stay near zero since the mock is its own source.
- All admin + fence + manual control messages ACK as they would on a real Jetson, but nothing actually happens to a Pixhawk.

## 5. Known follow-ups, not yet verified

- **Nothing has touched real hardware yet.** All verification is against the mock.
- **Fence upload uses the legacy FENCE_POINT protocol.** Still the most reliable path on ArduPilot 4.x, but worth swapping to the mission-protocol-with-MISSION_TYPE_FENCE approach if we hit issues.
- **Battery thresholds are guesses.** `warnV=12.0`, `failV=11.0` in `safety.js` assume 3S LiPo. Needs calibration against the actual pack the vehicle flies.
- **Gamepad path untested** — no physical controller available during development. The Gamepad API wiring is standard, should Just Work when a controller is plugged in.
- **GCS-side MediaRecorder needs a real video stream** — no camera frames in the mock, so the recording flow's happy path can't be end-to-end checked without hardware.
- **Jetson-side deploy not done.** Per the session snapshot in memory, `push-to-jetson.sh` is broken when run from this tool (hardcoded user + bypasses the SSH alias). User runs the deploy themselves, or `scp` individual files.
